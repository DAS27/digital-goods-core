# Проверка и фактическое время

## Локальный прогон 9 сентября 2026

Команда: `docker compose --profile test run --rm -e RUN_RANDOM_TESTS=1 tests`.

```text
Ran 28 tests in 30.404s
OK
```

Прогон выполнен после сборки актуального образа на чистой отдельной тестовой PostgreSQL. Проверены все шесть критериев приёмки исходного задания и дополнительные ошибки входных данных, восстановления и учёта.

- 50 параллельных одинаковых событий и 50 разных событий по одному заказу: одна оплата и одна физическая выдача.
- 12 гонок создания заказа и прихода оплаты, ранние события и переставленные paid/failed.
- Таймауты до и после выдачи, повтор с прежним request_id, окончательный отказ A и переход на B, пустой остаток и пополнение.
- Десять конкурентных workers, разные заказы и уникальные ключи, запрет изменения результата request_id.
- Неоднозначные 5xx, неверный JSON и несовпадающий request_id не разрешают переход на B.
- Два восстановленных состояния в окне падения и отдельный реальный SIGKILL worker после фиксации выдачи у поставщика.
- Отложенный повтор соблюдает записанный срок; потерянная задача восстанавливается без повторной оплаты.
- Несбалансированная проводка отклоняется с SQLSTATE 23514, вся транзакция откатывается.
- Сверка находит искусственно внесённую выдачу без оплаты; последующая обычная обработка восстанавливает согласованность.
- Каталог: одинаковые цены, курсоры, исключение неактивных товаров и нулевых остатков, ошибки параметров.
- Отдельный сценарий со случайными отказами обоих поставщиков; после восстановления все заказы выданы однократно.

## Каталог

Фактический PostgreSQL: **16.14**, Linux aarch64, локальный Docker. Проверка добавила 20 000 синтетических SKU к 52 существовавшим строкам: **20 052 SKU**. Вставки затем откатились. Полные SQL и `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` находятся в [BENCHMARK.json](BENCHMARK.json).

| Запрос | План доступа | Индекс | Строк | Execution Time |
|---|---|---|---:|---:|
| Первая страница key | Index Only Scan | catalog_type_price | 51 | 0,081 мс |
| Страница после курсора | Index Only Scan | catalog_type_price | 51 | 0,056 мс |

Берётся 51 строка: 50 для ответа и одна для определения следующей страницы. Индекс одновременно ограничивает тип, задаёт порядок цены/SKU и покрывает поля ответа. Курсор используется в Index Cond; полного прохода и сортировки нет. Возможные Heap Fetches видны в сохранённом плане: название Index Only Scan само по себе не означает нулевое число проверок видимости в таблице.

Это локальные замеры двух SQL-запросов на синтетическом распределении, без сетевого времени API. Они не являются обещанием production latency или throughput. HTTP и БД проверялись на настоящих процессах, а поставщики остаются заглушками по заданию.
