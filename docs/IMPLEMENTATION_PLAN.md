# План выполнения

Источник: [тестовое задание](https://docs.google.com/document/d/11ouRyL-sjW5110I6iRgPG_7WkPaJvUjTZjAE5Ta_OOo/edit). Начало работы: 2026-09-08, примерно 18:55 Asia/Almaty.

## Объём и оценка

Реализуются все пять этапов, включая бонусные. Оценка для одного опытного PHP-разработчика: **24–36 часов (3–5 рабочих дней)**. Это оценка инженерной работы, не обещание длительности агентного запуска. Фактическое время и результаты будут записаны отдельно.

| Этап | Работа и результат | Владелец | Оценка |
|---|---|---|---|
| 0 | Контракты API, инварианты, модель состояний, схема PostgreSQL | Координатор | 2–3 ч |
| 1 | Создание/получение заказа; inbox событий оплаты; дубли, ранние события, порядок, проверка суммы | Агент orders_payments | 4–6 ч |
| 2 | Два HTTP-поставщика: устойчивый request_id, пул ключей, управляемые и случайные отказы | Агент suppliers_delivery | 3–4 ч |
| 3 | Фоновая выдача, блокировка заказа, фиксация попытки до HTTP, backoff, безопасный fallback, восстановление | Агент suppliers_delivery | 5–7 ч |
| 4 | Автоматические проверки гонок, падений, таймаутов, ранних событий и пустого остатка | Агент adversarial_tests | 4–6 ч |
| 5 | Денежный журнал, сверка, каталог, индексы и EXPLAIN ANALYZE на 20 000 SKU | Координатор | 3–5 ч |
| 6 | Интеграция, Docker Compose, CI, README, ревью, запуск полного набора, GitHub | Координатор + агенты | 3–5 ч |

Время в таблице частично перекрывается и содержит округление; суммарная оценка 24–36 часов. Для команды из трёх исполнителей после согласования контрактов ориентир — 12–18 часов календарной работы с интеграцией и ревью. У агентного исполнения фактический срок зависит от доступности окружения и результатов проверок.

## Последовательность и зависимости

1. Зафиксировать инварианты и общий контракт в `docs/CONTRACT.md`, создать схему и каркас.
2. Параллельно реализовать заказы/платежи, поставщиков/worker и внешний тестовый стенд. Файлы разделены между владельцами; общие изменения согласуются с координатором.
3. Интегрировать API и worker. Проверить базовый путь создания, оплаты и выдачи.
4. Прогнать 50 параллельных одинаковых событий и 50 разных событий для одного заказа, затем отдельную гонку нескольких заказов за ограниченный остаток.
5. Проверить таймаут после выдачи, недоступность A, отказы обоих поставщиков, пустой остаток, перезапуск worker и восстановление.
6. Проверить сверку и баланс журнала; получить фактический план запроса на большом каталоге.
7. Исправить найденные проблемы, повторить затронутые проверки и выполнить весь приёмочный набор.
8. Подготовить инструкции запуска, ограничения и записку решений. Создать приватный `DAS27/digital-goods-core`, загрузить исходники и проверить состояние GitHub.

## Критерии готовности

- Все шесть сценариев приёмки воспроизводятся одной командой без ручной отправки запросов.
- Проверяется физическое количество выданных ключей у каждого поставщика, а не только статус заказа.
- Таймаут/невалидный ответ/неопределённый HTTP 5xx сохраняют привязку к поставщику и request_id.
- Fallback разрешён только при доказанном отсутствии выдачи; неоднозначная выдача восстанавливается повтором с прежним request_id.
- Событие оплаты и задача выдачи фиксируются атомарно; оплаченная задача не теряется после падения процесса.
- Денежные суммы хранятся целыми копейками, журнал сбалансирован и защищён ограничениями БД.
- Секреты, ключи доступа и локальные данные не входят в Git.
- В итоговом отчёте отдельно указаны выполненные проверки, ограничения и фактическое время.
